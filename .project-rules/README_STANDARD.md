# Стандарт README для проектов

## 1. Назначение

README должен быстро и точно ответить на вопросы:

1. Что это за проект?
2. Какую задачу он решает?
3. В каком состоянии находится?
4. Как его установить или запустить?
5. Какие ограничения нужно знать?
6. Где находится подробная документация?

README не заменяет полную документацию. Подробные инструкции, архитектурные решения, большие таблицы и историю версий следует хранить в `docs/` и `CHANGELOG.md`.

---

## 2. Обязательные файлы и языки

В каждом проекте используются два файла:

```text
README.md       — основная русская версия
README_EN.md    — английская версия
```

Другие схемы именования, например `README_RU.md`, не используются без отдельной причины.

GitHub автоматически показывает `README.md`, поэтому русская версия остаётся основной.

### Переключатель языка

Переключатель располагается в шапке после краткого описания и до основной навигации.

В `README.md`:

```markdown
**Русский** · [English](README_EN.md)
```

В `README_EN.md`:

```markdown
[Русский](README.md) · **English**
```

Активный язык выделяется жирным и не является ссылкой.

В основной части README языки не смешиваются. Названия технологий, команд, классов, протоколов и файлов сохраняются в исходном виде.

---

## 3. Единая шапка

Шапка всех проектов строится в одном порядке:

1. необязательный логотип;
2. единственный заголовок первого уровня;
3. описание проекта в одном или двух предложениях;
4. переключатель языка;
5. от нуля до пяти полезных badges;
6. короткая навигация по ключевым разделам.

Базовый вариант:

```markdown
<div align="center">

<img src="docs/assets/logo.png" width="128" alt="<Название проекта>">

# <Название проекта>

<Что делает проект и для кого он предназначен. Одно или два предложения.>

**Русский** · [English](README_EN.md)

[![Release](...)](...)
[![Build](...)](...)
[![License](...)](...)

[Быстрый старт](#быстрый-старт) ·
[Документация](#документация) ·
[Релизы](../../releases)

</div>
```

Логотип, badges и строка навигации необязательны. Пустые декоративные элементы не добавляются.

---

## 4. Обязательные заголовки

Эти разделы присутствуют во всех проектах и идут в указанном порядке.

| Порядок | `README.md` | `README_EN.md` | Назначение |
|---:|---|---|---|
| 1 | `## О проекте` | `## About` | назначение, пользователь, основная задача |
| 2 | `## Статус проекта` | `## Project status` | стадия, стабильность, готовность основных сценариев |
| 3 | `## Возможности` | `## Features` | только реально реализованные функции |
| 4 | `## Быстрый старт` | `## Quick start` | кратчайший рабочий путь до результата |
| 5 | `## Документация` | `## Documentation` | ссылки на подробные документы |
| 6 | `## Ограничения` | `## Limitations` | известные ограничения, неподдерживаемые сценарии |
| 7 | `## Лицензия` | `## License` | лицензия проекта и ссылка на файл |

Обязательные разделы нельзя оставлять пустыми.

Если проект находится на ранней стадии, это пишется прямо:

```markdown
## Быстрый старт

Публичная сборка пока не подготовлена. Текущий код запускается только из среды разработки.
```

Это лучше, чем выдуманная команда или обещание будущего релиза.

## 5. Каталог условных заголовков

Условные разделы добавляются только при наличии полезного содержания. Их относительный порядок фиксирован.

| Позиция | `README.md` | `README_EN.md` | Когда использовать |
|---:|---|---|---|
| 1 | `## Скриншоты` | `## Screenshots` | есть актуальные изображения интерфейса |
| 2 | `## Требования` | `## Requirements` | нужны конкретные ОС, SDK, runtime, права или оборудование |
| 3 | `## Установка` | `## Installation` | установка требует больше нескольких шагов |
| 4 | `## Использование` | `## Usage` | после установки нужны отдельные пользовательские сценарии |
| 5 | `## Режимы работы` | `## Operating modes` | проект имеет несколько явно различимых режимов |
| 6 | `## Конфигурация` | `## Configuration` | есть параметры, `.env`, JSON, UI-настройки или профили |
| 7 | `## Команды` | `## Commands` | есть CLI, PowerShell, Gradle tasks или команды менеджера |
| 8 | `## API` | `## API` | проект предоставляет внешний программный интерфейс |
| 9 | `## Архитектура` | `## Architecture` | схема помогает понять компоненты или поток данных |
| 10 | `## Безопасность` | `## Security` | есть секреты, права, модель доверия или существенные риски |
| 11 | `## Приватность` | `## Privacy` | проект собирает, хранит или передаёт пользовательские данные |
| 12 | `## Диагностика` | `## Troubleshooting` | есть типичные ошибки и понятный путь проверки |
| 13 | `## Обновление` | `## Updating` | обновление отличается от повторной установки |
| 14 | `## Резервное копирование и миграция` | `## Backup and migration` | есть переносимые данные или состояние |
| 15 | `## Разработка` | `## Development` | нужны правила локальной разработки |
| 16 | `## Сборка` | `## Build` | проект собирается из исходников |
| 17 | `## Тестирование` | `## Testing` | есть реальные команды автоматических или ручных проверок |
| 18 | `## Дорожная карта` | `## Roadmap` | опубликован ограниченный и актуальный план |
| 19 | `## Участие в разработке` | `## Contributing` | принимаются внешние изменения |
| 20 | `## Происхождение и благодарности` | `## Credits` | есть upstream, форк, заимствованный код или значимые авторы |

## 7. Синхронизация русского и английского README

Обе версии должны описывать одну и ту же фактическую версию проекта.

Обязательные правила:

1. В обеих версиях выбран одинаковый набор разделов.
2. Разделы идут в одинаковом порядке.
3. Таблицы, команды, версии и ссылки совпадают.
4. Реализованные, экспериментальные и планируемые функции имеют одинаковый статус.
5. Изменение факта в одном README требует изменения второго.
6. Английский текст является естественным переводом, а не дословной калькой.
7. Нельзя обновлять только шапку одной версии.
8. Нельзя оставлять устаревшую команду в одном языке.
9. Якорные ссылки внутри каждого файла используют заголовки его языка.
10. Ссылки между языками всегда относительные: `README.md` и `README_EN.md`.

Если английская версия временно отстаёт, это нужно исправить до слияния изменения документации. Предупреждение «translation may be outdated» не должно становиться постоянной заменой синхронизации.

## 8. Фактическая точность

README описывает только подтверждённое состояние проекта.

Допустимые основания:

```text
исходный код;
файл конфигурации;
результат команды;
автоматический тест;
ручная проверка;
актуальная документация;
релизный артефакт;
явно зафиксированное решение.
```

Нельзя:

- писать о функции, которой нет в текущем коде;
- смешивать roadmap с реализованными возможностями;
- утверждать, что сборка или тесты проходят, если они не запускались;
- указывать неподтверждённую совместимость;
- придумывать версии, команды, пути, badges или ссылки;
- публиковать реальные токены, пароли, приватные URL и персональные данные.

Для непроверенного состояния используются прямые формулировки:

```text
Не проверено на Windows 10.
Ручной сценарий пока не пройден.
Поддержка Linux не заявлена.
Функция экспериментальная.
Публичный релиз пока не подготовлен.
```

## 9. Правила естественного текста

README не должен выглядеть как набор автоматически заполненных секций.

### Требуется

- каждое предложение сообщает новый факт;
- первый абзац сразу описывает проект;
- конкретные имена команд, файлов и сценариев заменяют общие слова;
- статус функции обозначается прямо;
- ограничения сообщаются без смягчающей рекламы;
- технический термин используется одинаково во всём документе;
- длина раздела соответствует объёму полезной информации.

### Удаляется при редактуре

- вступление, повторяющее название проекта;
- заключение, пересказывающее README;
- искусственные наборы из трёх или четырёх одинаковых карточек;
- одинаковые по форме абзацы без содержательной причины;
- лишние заголовки из одного предложения;
- повтор одной возможности в шапке, разделе «О проекте» и разделе «Возможности»;
- слова «мощный», «современный», «гибкий», «надёжный», «масштабируемый» без конкретного основания;
- фразы «Важно отметить», «Следует учитывать», «В современном мире», если после удаления смысл не меняется;
- обещания «простая установка» или «быстрый запуск», если процесс действительно сложный.

### Плохо

```text
Проект предоставляет мощное, гибкое и современное решение для различных сценариев.
```

### Лучше

```text
Приложение переключает DNS-профили из WPF-интерфейса, системного трея и CLI.
Все три клиента используют один файл `profiles.json`.
```

## 10. Стиль оформления

### Заголовки

- В документе один `#` — название проекта.
- Основные разделы используют `##`.
- Вложенные части используют `###`.
- Заголовок не дублируется с соседним абзацем.
- Заголовки в русской и английской версиях выбираются только из каталога, кроме предметных подразделов третьего уровня.

### Badges и цветная панель ссылок

В шапке рекомендуется использовать 3–5 badges в стиле `for-the-badge`.
Они одновременно показывают состояние проекта и работают как ссылки.

Рекомендуемый набор:

1. последний релиз;
2. состояние основной CI-сборки;
3. платформа или runtime;
4. документация;
5. лицензия.

Готовая основа:

```markdown
[![Release](https://img.shields.io/github/v/release/<OWNER>/<REPO>?display_name=tag&sort=semver&style=for-the-badge&logo=github&label=release)](../../releases)
[![Build](https://img.shields.io/github/actions/workflow/status/<OWNER>/<REPO>/<WORKFLOW>.yml?branch=main&style=for-the-badge&logo=githubactions&logoColor=white&label=build)](../../actions)
[![Platform](https://img.shields.io/badge/platform-<PLATFORM>-0A7EA4?style=for-the-badge)](#требования)
[![Documentation](https://img.shields.io/badge/docs-open-4C8BF5?style=for-the-badge&logo=readthedocs&logoColor=white)](#документация)
[![License](https://img.shields.io/github/license/<OWNER>/<REPO>?style=for-the-badge&label=license)](LICENSE)
```

Обязательные правила:

- заменить все placeholders реальными значениями;
- удалить badge, если соответствующего релиза, workflow, лицензии или раздела нет;
- не указывать зелёный статус вручную вместо реального состояния CI;
- не добавлять случайные badges только ради цвета;
- проверить, что badge и его ссылка открывают ожидаемую страницу;
- использовать одинаковую панель в `README.md` и `README_EN.md`;
- локальные якоря менять по языку: `#требования` и `#requirements`;
- не превышать пять badges без конкретной причины.

После панели badges размещается обычная текстовая навигация:

```markdown
[Быстрый старт](#быстрый-старт) ·
[Документация](#документация) ·
[Релизы](../../releases) ·
[Сообщить об ошибке](../../issues)
```

Она остаётся доступной при блокировке внешних изображений и лучше читается на мобильных устройствах.

### Изображения

- логотип: примерно 96–160 px;
- изображения хранятся в `docs/assets/`;
- скриншоты имеют одинаковую ширину или высоту;
- каждый `<img>` содержит точный `alt`;
- устаревший скриншот удаляется или обновляется;
- изображение не заменяет инструкцию.

### Таблицы

Таблица используется для сравнения однотипных данных:

- режимов;
- платформ;
- параметров;
- команд;
- разрешений;
- статусов.

Один факт не оформляется таблицей.

### Блоки предупреждений

Используются по смыслу:

```markdown
> [!NOTE]
> Дополнительная информация.

> [!IMPORTANT]
> Условие, без которого основной сценарий не работает.

> [!WARNING]
> Риск неправильной настройки или потери работоспособности.

> [!CAUTION]
> Риск потери данных, утечки секрета или небезопасного действия.
```

Предупреждения не используются как декоративные цветные блоки.

## 11. Разделы, которые не следует раздувать

### Возможности

Только наблюдаемые функции. Не повторять архитектуру и roadmap.

### Быстрый старт

Кратчайший путь до рабочего результата. Подробности переходят в «Установку» или отдельный документ.

### Архитектура

В README достаточно одной схемы и краткого объяснения. Полное решение хранится в `docs/architecture/`.

### Документация

Ссылки группируются по задаче. Не перечислять архивные и внутренние файлы без пользы пользователю.

### Дорожная карта

Только ближайшие подтверждённые этапы. Идеи без решения хранятся отдельно.

### Лицензия

Одно или два предложения и ссылка на `LICENSE`.

---

## 12. Процедура создания README

1. Определить тип проекта и основного читателя.
2. Проверить код, команды, версии, релизы и существующую документацию.
3. Выбрать разделы из общего каталога.
4. Создать `README.md`.
5. Создать `README_EN.md` с тем же набором разделов.
6. Проверить все относительные ссылки.
7. Проверить команды и пути.
8. Удалить пустые, повторяющиеся и декоративные разделы.
9. Сравнить обе версии по структуре и фактам.
10. Выполнить чек-лист перед публикацией.

## 13. Именование и структура файлов

Рекомендуемая структура:

```text
project-root/
├── README.md
├── README_EN.md
├── LICENSE
├── CHANGELOG.md
├── AGENTS.md
└── docs/
    ├── assets/
    │   ├── logo.png
    │   └── screenshots/
    ├── architecture/
    ├── development/
    ├── testing/
    └── releases/
```

Внутренние приватные правила не должны быть доступны из публичного README.

README может ссылаться на публичную документацию, но не должен раскрывать существование или содержимое приватных файлов с правилами проекта.
