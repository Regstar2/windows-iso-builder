# Именование новых проектов и репозиториев

Этот документ задаёт единый стиль для новых проектов.
Он применяется до создания каталога проекта, GitHub-репозитория, CI и публичных ссылок.

## 1. Рекомендуемый формат

По умолчанию имя нового репозитория и корневого каталога записывается в формате:

```text
lowercase-kebab-case
```

Примеры:

```text
dns-switcher
whitelist-checker
tg-ws-proxy-android
wdtt-home-gateway
notify-mark
music-ark
```

Название продукта внутри README, интерфейса и релизов может использовать собственный регистр:

```text
Репозиторий: tg-ws-proxy-android
Продукт: TgWsProxy Android
```

## 2. Почему используется дефис

Дефис `-` выбран как разделитель слов по следующим причинам:

1. Имя остаётся читаемым в URL:
   `github.com/owner/tg-ws-proxy-android`.
2. Имя удобно вводить в терминале и скриптах: нет пробелов и кавычек.
3. Строчные буквы уменьшают риск различий между регистрозависимыми и
   регистронезависимыми файловыми системами.
4. Формат хорошо подходит для GitHub, CI, имён архивов, контейнеров и
   связанных репозиториев.
5. Семейство компонентов легко получает общий префикс:

   ```text
   tg-ws-proxy-android
   tg-ws-proxy-server
   tg-ws-proxy-worker
   ```

Дефис не является техническим требованием GitHub.
`snake_case`, `PascalCase` и другие варианты могут работать, но смешивать
несколько стилей в новых репозиториях без причины не следует.

## 3. Когда допустимо отступление

Другой формат допустим, если существует конкретное техническое или
экосистемное требование.

Примеры:

- имя импортируемого Python-модуля использует `snake_case`;
- package name, application ID или namespace подчиняется правилам платформы;
- upstream-проект уже имеет устойчивое имя, которое нужно сохранить;
- репозиторий является временным fork без собственной идентичности;
- официальное название содержит формат, изменение которого ухудшит узнаваемость.

При этом технические идентификаторы не обязаны совпадать:

```text
GitHub-репозиторий: my-python-tool
Python-модуль: my_python_tool
Публичное название: My Python Tool
```

Отступление должно быть осознанным, а не случайным.

## 4. Правила для новых репозиториев

Использовать:

- латинские строчные буквы;
- цифры, если они являются частью устойчивого названия;
- один дефис между словами;
- от двух до четырёх коротких смысловых частей.

Не использовать без необходимости:

```text
project
app
application
program
tool
new
final
final2
test
demo
temp
official
```

Не включать в постоянное имя:

- номер версии;
- дату;
- статус `alpha`, `beta`, `rc`;
- номер попытки;
- временные слова;
- имя ветки.

Неправильно:

```text
DnsSwitcher
TgWsProxy_Android
white-list-checker-final
notify-mark-v2
new-project-2026
```

Предпочтительно:

```text
dns-switcher
tg-ws-proxy-android
whitelist-checker
notify-mark
```

## 5. Платформа и назначение

Платформа или роль добавляется только тогда, когда она различает несколько
связанных проектов.

Допустимые уточнения:

```text
-android
-windows
-linux
-desktop
-web
-server
-client
-api
-worker
-bot
-cli
-sdk
-docs
-infra
```

Плохо:

```text
notify-mark-android-app-project
```

Лучше, если другой реализации нет:

```text
notify-mark
```

При нескольких реализациях:

```text
notify-mark-android
notify-mark-desktop
```

## 6. Существующие репозитории

Эти правила обязательны для новых проектов.

Существующие репозитории не переименовываются автоматически только ради
единообразия. Переименование выполняется отдельной задачей после проверки:

- ссылок и badges;
- GitHub Actions;
- deploy hooks и webhooks;
- документации;
- package registries;
- локальных Git remote;
- внешних интеграций;
- release-архивов и скриптов.

Имя репозитория не должно автоматически менять package name, application ID,
namespace, домен или имя продукта.

## 7. Проверка перед созданием проекта

```text
[ ] Назначение проекта сформулировано одним предложением.
[ ] Публичное название продукта определено отдельно.
[ ] Имя репозитория записано в lowercase-kebab-case либо отступление обосновано.
[ ] В имени нет версии, даты, стадии и временных слов.
[ ] Платформа или роль добавлена только при необходимости.
[ ] Имя не конфликтует с существующим репозиторием владельца.
[ ] Корневой каталог использует то же техническое имя.
[ ] README использует публичное название продукта.
[ ] Package name, application ID и namespace выбраны отдельно по правилам платформы.
```

## 8. Требования к AI-агенту

Перед созданием нового проекта или репозитория AI-агент обязан:

1. Прочитать этот файл.
2. Разделить публичное название продукта и техническое имя репозитория.
3. Использовать `lowercase-kebab-case` по умолчанию.
4. При отступлении указать конкретную техническую причину.
5. Не создавать репозиторий с временным именем.
6. Не переименовывать существующий репозиторий без явного требования.
7. Не менять package name, application ID, namespace или домен автоматически.
8. Использовать выбранное техническое имя последовательно в каталогах,
   командах Git, CI, документации и release-артефактах.
